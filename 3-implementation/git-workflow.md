# Робота з git (практичні 10–11)

> Цей крок виконує команда сама: історія з гілками, pull request із ревʼю і розвʼязаним конфліктом має бути справжньою й видимою в `git log --graph`.

## Правила

- `main` — завжди робочий стан, CI зелений.
- Гілка на задачу або документ: `docs/srs`, `feat/interests`, `fix/bug-03-latency`.
- Повідомлення коміту — що змінено, зрозуміло без відкриття файлу: `docs: додати правила валідації інтересів`.
- Злиття в `main` — лише через pull request з ревʼю іншої людини.

## Pull request із ревʼю

```bash
git switch -c docs/test-plan
# редагуємо 4-quality/test-plan.md
git add 4-quality/test-plan.md
git commit -m "docs: тест-план, критерії входу й виходу"
git push -u origin docs/test-plan
gh pr create --fill          # або через вебінтерфейс GitHub
```

Рецензент лишає коментар, автор виправляє, рецензент натискає **Approve**, PR зливається.

## Конфлікт злиття

1. А і Б створюють гілки від однієї версії `main` і правлять **той самий рядок** у `1-lifecycle/backlog.md` (наприклад, статус задачі 10).
2. А зливає свій PR першим.
3. Б оновлює гілку: `git switch docs/backlog-b && git merge main` — git повідомляє про конфлікт.
4. Б відкриває файл, обирає правильний варіант між маркерами `<<<<<<<`, `=======`, `>>>>>>>`, видаляє маркери.
5. `git add 1-lifecycle/backlog.md && git commit` — коміт злиття з розвʼязаним конфліктом; push; PR зливається.

## Перевірка

```bash
git log --graph --oneline --all
```

Має бути видно щонайменше одне відгалуження, PR-злиття і коміт розвʼязання конфлікту.
